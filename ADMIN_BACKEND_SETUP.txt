HOW IT WORKS
═════════════════════════════════════════════════════════════════════════════

1. User visits /admin login page
   ↓
2. Enters username & password
   ↓
3. Frontend calls: POST /api/admin/login/
   └─ Backend verifies credentials against ADMIN_USERS dict
   ↓
4. Backend returns token (if valid)
   ↓
5. Frontend stores token in localStorage
   ↓
6. Frontend redirects to /admin/dashboard
   ↓
7. Protected pages check token with GET /api/admin/verify/
   └─ Backend verifies token is valid & not expired
   ↓
8. If valid: Show page
   If invalid: Redirect to /admin login

SECURITY ARCHITECTURE
═════════════════════════════════════════════════════════════════════════════

Backend-Only Benefits:
  ✓ Passwords never sent to frontend
  ✓ Passwords never stored in browser
  ✓ Credentials verified on secure backend
  ✓ Frontend only has temporary token
  ✓ Backend can implement rate limiting
  ✓ Backend can log all auth attempts
  ✓ Easy to add password hashing later

Data Flow:
  Browser               Backend                Database
     │                    │                       │
     ├─ username/pass ──→ │                       │
     │                    ├─ query ───────────→   │
     │                    ←─ user data ──────────┤
     │                    │ (verify password)     │
     │  ← token ─────────┤                       │
     │  (store in localStorage)                  │
     │                    │                       │
     ├─ token ────────────→                       │
     │ (with each request)│ (verify & validate)  │
     │  ← response ──────┤                       │

TOKEN SYSTEM
═════════════════════════════════════════════════════════════════════════════

Token:
  • Generated: When user logs in
  • Stored: Backend ADMIN_SESSIONS dict (in-memory)
  • Sent: With Authorization header (Bearer token)
  • Verified: On /api/admin/verify/ calls
  • Expires: After 24 hours
  • On Logout: Deleted from ADMIN_SESSIONS

Frontend Storage:
  • Key: admin_session
  • Value: { id, username, token, loggedInAt }
  • Format: JSON in localStorage
  • Cleared: On logout or expiration

TROUBLESHOOTING
═════════════════════════════════════════════════════════════════════════════

"Cannot connect to API"
  1. Check backend is running: http://localhost:5000/api/health
  2. Check .env.local has correct NEXT_PUBLIC_API_URL
  3. Restart frontend dev server
  4. Check CORS is enabled in backend (already configured)

"Login fails with valid credentials"
  1. Check credentials are exact (case-sensitive)
  2. Check ADMIN_USERS in backend/api/admin_views.py
  3. Restart backend
  4. Check browser console for error details

"Token verification fails"
  1. Token expires after 24 hours - login again
  2. Check Authorization header is sent correctly
  3. Verify backend is running
  4. Check session hasn't been cleared

COMPARING OLD vs NEW
═════════════════════════════════════════════════════════════════════════════

OLD (Frontend → Supabase):
  Frontend connects directly to Supabase
  ✗ Exposes Supabase URL and keys
  ✗ Passwords sent to frontend
  ✗ Hard to add rate limiting
  ✗ Hard to add audit logging

NEW (Frontend → Backend → Supabase):
  Frontend connects to Backend only
  ✓ No Supabase exposure to frontend
  ✓ Passwords handled by backend only
  ✓ Easy to add rate limiting
  ✓ Easy to add audit logging
  ✓ More secure architecture
  ✓ Better separation of concerns
